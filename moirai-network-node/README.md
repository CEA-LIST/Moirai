# Moirai network node

A small runtime for static-membership Moirai replicas. TCP is the default
transport. Commitment and leader selection belong to `moirai-protocol`; this
crate contains no oracle implementation, heartbeat protocol, or commitment
algorithm.

## Build and run

Run from the repository root:

```sh
cargo build --manifest-path moirai-network-node/Cargo.toml --examples
cargo run --manifest-path moirai-network-node/Cargo.toml --example vanilla_set -- moirai-network-node/examples/config_a.json
cargo run --manifest-path moirai-network-node/Cargo.toml --example vanilla_set -- moirai-network-node/examples/config_b.json
```

Run the last two commands in separate terminals. Use `commit_set` at **every**
replica to run the majority-commitment example. `examples/config_solo.json` runs
one replica. The crate has its own workspace boundary and lockfile so the parent
workspace does not need editing. Binaries are generated under
`moirai-network-node/target/debug/examples/`.

| Example | Child data type | Commitment |
| --- | --- | --- |
| `vanilla_set` | Core `CommitSet<String>` | `CommitmentLog<_, LamportCommit>`; waits for all configured members |
| `commit_set` | Core `CommitSet<String>` | `CommitmentLog<_, OmegaCommit<EventOracle>>`; majority commitment |

Both implement sequential set operations, ordered by the core Lamport policy,
and support `Add`, `Remove`, `Clear`, and `NoOp`. This replaces the obsolete AWSet
examples and their removed core APIs. Concurrent operations follow the core
policy's timestamp and replica-ID tie-breaking rules.

## Architecture

One owner thread holds the core `Replica<L, Tcsb<L::Update>>`. Each iteration
processes incoming network messages and bounded client work, sends periodic
pulls/idle no-ops, resolves commitment waits, and optionally samples log memory.
There are no locks around the replica, background oracle workers, connectivity
maps, operation-history endpoints, or pause/resume controls.

| Module | Responsibility |
| --- | --- |
| `node` | Replica loop, client channel, timers, optional protocol hook |
| `transport` | Byte-oriented `Transport` trait and complete incoming `Packet`s |
| `tcp` | Persistent connections, framing, bounded queues, reconnection |
| `wire` | Compact bincode DTOs built through public core APIs |
| `http_api` | Three routes, translated into requests to the replica thread |
| `config` | JSON configuration and static numeric membership |

HTTP workers wait for replies independently, so a strong update waiting for
commitment does not block local reads or weak updates. The client request queue
is bounded at 256. HTTP optimistic/read workers and consistent
workers have independent limits (`http_optimistic_limit` and
`http_consistent_limit`, both defaulting to 64). Pending commitment waits are
bounded by `http_consistent_limit` too. Health probes are handled separately so waiting updates
cannot consume their capacity. An overloaded or stopped API returns a failure status.
Health requests also pass through the owner loop, making Kubernetes probes
check that the replica loop is responding.

### Custom applications and external commitment protocols

Supply a core log and an `Application<L>` with three callbacks:

- `query`: convert a local query result to JSON;
- `committed`: test whether an update ID belongs to the protocol's committed
  frontier;
- `no_op`: construct an always-enabled command that leaves application state
  unchanged while advancing protocol metadata.

Commands must deserialize from JSON and be `Send`. Replicated updates must
support serde serialization/deserialization. Logs implement `IsLog` and
`DeepSizeOf`; the latter preserves Kubernetes log-memory measurements. The
`test_utils` core feature enables the public replica/log accessors and size
implementations used here. Commands and replicated updates can be different
types: HTTP accepts a command, while commitment metadata is generated by the
core log's `prepare` method.

```rust,ignore
let mut node = Node::new(config, log, application)?;
node.run(None)?;

// Or pass an additional callback. It can capture external protocol state.
let mut drive_protocol = |node: &mut Node<MyLog>| {
    external_protocol.poll(node.replica_mut())?;
    if let Some(command) = external_protocol.next_command() {
        node.broadcast(command)?;
    }
    Ok(())
};
node.run(Some(&mut drive_protocol))?;
```

The callback runs once per iteration after normal processing. Keep it short and
nonblocking. Use `broadcast` for new commands so they are both locally applied
and pushed to peers; calling the core `send` method directly only applies them
locally. `replica_mut`, `transport_mut`, and the application commitment predicate
allow integration with other log/protocol implementations. `tick()` embeds one
iteration in an external loop without starting HTTP. `handle()` returns a
thread-safe client handle; `handle.stop()` ends `run` cooperatively and resolves
pending requests. A hook error also stops the run and resolves pending requests.
Both built-in examples use `run(None)`: the core handles their protocols without
an extra worker or hook.

### Additional transports

Implement `Transport::send(peer, Arc<[u8]>)` and `Transport::poll()` and use
`Node::with_transport`. The adapter supplies the configured sender ID and
complete byte payloads. It must perform bounded work, preserve partial I/O, and
either queue an entire message or reject it. TCP additionally verifies the wire
version and full static member list during connection setup. Other adapters must
provide the same identity/membership agreement. No oracle interface is required.

## Configuration

```json
{
  "replica_id": 1,
  "replica_name": "a",
  "listen_port": 19001,
  "http_port": 8081,
  "peers": [{"replica_id": 2, "replica_name": "b", "address": "127.0.0.1:19002"}],
  "pull_interval_ms": 500,
  "pull_peer_count": 1,
  "noop_interval_ms": 1000,
  "event_timeout_ms": 10000,
  "request_timeout_ms": 25000,
  "http_optimistic_limit": 64,
  "http_consistent_limit": 64,
  "memory_usage_enabled": true,
  "memory_usage_interval_ms": 1000
}
```

IDs are unsigned **16-bit** numbers (`0..=65535`), matching the core's
`StableReplicaId`. IDs must be unique, and a peer cannot have the local ID.
Every node must use the same complete static membership. Core replica IDs are
canonical decimal strings; display names do not affect identity or ordering.
`replica_id` and `listen_port` are required. Names default to empty strings,
peers to an empty list, and `http_port` to `null` (HTTP disabled). The other
defaults are shown above. Timer values must be positive; `noop_interval_ms` also
accepts `null`.

HTTP limits must be positive integers and count concurrent requests, not requests
per second. Consistent requests hold their slot while waiting for commitment;
optimistic updates and state reads use the other budget. A full budget returns
HTTP 503 with `request_class` identifying the exhausted budget. Both classes
still share CPU, the replica loop, and the bounded client queue. Each admitted
HTTP worker is an OS thread, so raising limits also increases thread, connection,
and memory requirements. A useful sizing estimate is arrival rate per replica
multiplied by response time, with headroom for bursts. There is no fixed measured
throughput guarantee for these defaults.

- **Pulls:** every `pull_interval_ms`, request missing events from up to
  `pull_peer_count` peers, rotating fairly through the peer list. Zero peers
  disables periodic pulls. A pull transmits the current vector clock and buffered
  event exceptions; replies contain missing history, split into bounded frames.
  Empty replies are suppressed. Disconnected/full peer queues are skipped and
  subsequent pulls repair dropped pushes and replies.
- **Idle no-ops:** after `noop_interval_ms` without a client update, emit a normal
  replicated no-op, then repeat at that interval until client updates resume.
  Client updates reset the deadline, including rejected updates. Reads, incoming
  remote events, and pulls do not reset it. Disabled no-ops leave idle commitment
  and event-driven leader progress dependent on client traffic.
- **Event timeout:** `commit_set` constructs the core `EventOracle` with
  `event_timeout_ms` and the local ID as fallback. The core oracle observes
  causally delivered event origins inside `OmegaCommit`. No external observer or
  heartbeat traffic is added. Choose a no-op interval comfortably below the
  event timeout, allowing for network and scheduling delays.

`heartbeat_interval_ms` is accepted as a legacy alias for `event_timeout_ms`;
provide only one of those fields. Old `oracle_mode` and `heartbeat_peer_count`
fields are ignored. `commit_set` always uses the core `EventOracle`.

## Minimal HTTP API

| Route | Behavior |
| --- | --- |
| `GET /api/health` | Responding replica loop, numeric ID and display name |
| `GET /api/state` | Local query result under `state`, plus identity fields |
| `POST /api/op` | Weak update: respond after local application |
| `POST /api/op?wait_for_commit=true` | Strong acknowledgment: wait for the application's commitment predicate |

`?wait_for_commit=false` is also accepted. For example:

```sh
curl --fail http://localhost:8081/api/op \
  -H 'Content-Type: application/json' -d '{"Add":"apple"}'
curl --fail 'http://localhost:8081/api/op?wait_for_commit=true' \
  -H 'Content-Type: application/json' -d '{"Remove":"apple"}'
curl --fail http://localhost:8081/api/state
```

A successful update returns `{"success":true,"applied":true,"message":"ok"}`.
Malformed JSON returns 400, oversized HTTP bodies 413, rejected commands 422,
and API overload/unavailability 503. A commitment timeout returns **HTTP 504**
with `success:false, applied:true`; it does not roll back the update. The default
25-second timeout fits within the launcher's 30-second client deadline.
Local reads include tentative updates and provide no linearizable read barrier.
Other routes return 404.

## Wire format and transport behavior

TCP uses one persistent bidirectional connection per pair; the smaller numeric
ID initiates it. A framed setup message carries `MRN1`, a two-byte sender ID, and
the sorted two-byte member IDs. All later frames have just a four-byte network
byte-order length prefix followed by the bincode payload. TCP enables Nagle
avoidance and kernel keepalive (2 seconds idle, 1 second probe interval, 3
unanswered probes). These are kernel connectivity checks, separate from the
event-driven commitment oracle.

The payload contains only an event, a pull, or a batch. It uses variable-width
integers, canonical numeric member slots, and vector clocks. Membership strings,
resolvers, redundant event sequence numbers, and Lamport timestamps are omitted;
the receiver reconstructs them. Serde `Option::None` carries only a one-byte
presence tag and **no absent-item payload**. For example, a small-vote
`SupportOp` with no previous partial adds three bytes over its child update:
vote, partial flag, and option presence. A present reference adds only its
compact origin and sequence fields. Do not use serde `skip_serializing_if` on
binary payload fields, since positional binary decoding needs their tags.

Frames are capped at 1 MiB. Each connection's output is bounded by 256 frames
and 4 MiB; broadcasts share immutable payload allocations across connections.
Partial reads/writes survive loop iterations. A poll makes at most one outgoing
connection attempt, with a 10 ms timeout; retries for that peer wait 500 ms.
Oversized local events are preflighted before application. Normal `prepare`
implementations should be pure; if a subsequent encode fails after application,
the HTTP result records that the update was applied.

Queued messages are discarded on disconnect and are repaired by later pulls.
There is no persistent storage, state transfer, dynamic membership, encryption,
or authentication. Use trusted peers. A replica that loses its in-memory state
cannot recover history already pruned at every donor. TCP reliability alone does
not guarantee recovery of a restarted replica. All members must use the same
example/payload schema; this wire format is incompatible with the old node.

## Kubernetes and measurements

The [launcher](../kubernetes-launcher/README.md) builds these examples with
`REPLICA_EXAMPLE=vanilla_set` (default) or `commit_set`. Its client routes,
readiness/liveness probes, ports, and result formats remain supported. The
launcher template forwards the new timeout/no-op settings. Experiment notebooks
and result-processing code require no changes.

When enabled, stdout contains one JSON log-memory record per configured interval:

```json
{"type":"log_memory_usage","replica_id":1,"replica_name":"a","timestamp_unix_ms":1790000000000,"log_memory_bytes":1234}
```

Only `replica.state().deep_size_of()` is measured, including the child log and
commitment metadata. This excludes TCSB history, transport/client queues, and
process RSS. The first sample occurs after one interval; delayed sampling emits
one current record. Disable measurements with `memory_usage_enabled:false`.

## Validation

```sh
cargo fmt --manifest-path moirai-network-node/Cargo.toml --check
cargo test --manifest-path moirai-network-node/Cargo.toml --all-targets --offline
cargo test --manifest-path moirai-network-node/Cargo.toml --doc --offline
```

Tests cover compact optional metadata, resolver order translation, causal
buffering/duplicates, pull repair and frame splitting, idle timers, commitment
waits/timeouts, majority progress after leader loss, protocol callbacks,
shutdown, HTTP concurrency, partial TCP frames, queue bounds, and reconnection.
